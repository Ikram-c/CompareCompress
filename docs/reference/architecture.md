# Architecture and source layout

CompressCompare is a C++17 program of about 15 000 lines in two CMake targets: **`cc_core`**, a static
library with no UI or OpenGL dependency (everything the tests exercise), and **`compresscompare`**, the
Dear ImGui / GLFW / OpenGL 3.3 application on top of it (`CompressCompare.app` on macOS). The image pipeline
is built on OpenCV 4.12; its heavy steps run through OpenCL when a trustworthy device is available and on
the CPU otherwise. The API reference generated by Doxygen ([how-to](../how-to/generate-api-docs.md))
documents every symbol; this page is the map.

## Directory layout

```
CMakeLists.txt          targets, options, tests, cc_bench, cppcheck / docs targets, install rules, the macOS bundle
CMakePresets.json       macos-intel, macos-intel-debug, linux-system
cmake/Dependencies.cmake   OpenCV from deps/ (or installed); find_package -> pkg-config -> FetchContent for the rest; warning flags
cmake/EmbedFile.cmake      turns config/config.yaml into a byte array header at build time
scripts/build-macos.sh  one-command macOS build: CMake if missing, OpenCV, configure, build, test, install, ad-hoc signing
scripts/build-deps.sh   static OpenCV 4.12.0 (core, imgproc, imgcodecs, videoio) into deps/opencv
packaging/macos/        Info.plist.in (minimum macOS 12.0, Retina capable) and the app icon
Doxyfile                API reference configuration
.clang-tidy             static-analysis checks (see Design principles)
config/config.yaml      every tunable value and the site database; embedded into the executable
src/util/               strings.h (string / URL / byte helpers), contract.h (CC_REQUIRE / CC_ENSURE)
src/core/               the library: config, OpenCV / OpenCL set-up, image I/O, JPEG parser, metrics and their kernels,
                        video, fuzzy search, sites, net, process, ffmpeg, threading
src/gpu/                gl.h (explicit OpenGL 3.3 loader), shaders.h (GLSL), renderer (textures, compare quad)
src/app/                App state and background jobs, the three UI files, the fuzzy site combo, ui_style.h
src/platform/           native file dialogs (osascript on macOS, zenity / kdialog on Linux)
src/main.cpp            command line, configuration, OpenCV start-up, window, ImGui, main loop
tests/                  eight ctest programs plus test_util.h (a small check framework)
tools/                  cc_bench.cpp (CPU / OpenCL benchmark), gen_config_reference.py, gen_site_reference.py,
                        check_function_length.py
docs/                   this documentation (Diátaxis: tutorials, how-to, reference, explanation)
samples/                synthetic test images and clips used by the tutorials, the tests and the smoke test
deps/                   created by the build scripts: OpenCV sources, build tree and install; CMake and NASM if needed
```

## Dependency direction

```
main.cpp ──> app ──> gpu ──> core ──> util
               │       │       ├──> OpenCV (core, imgproc, imgcodecs, videoio) ──> OpenCL, AVFoundation* / FFmpeg libraries**
               │       │       ├──> ImageIO, CoreGraphics* (imageio_apple.cpp)
               │       │       └──> yaml-cpp, libcurl (optional)
               │       └──> OpenGL (entry points loaded at run time)
               ├──> platform (dialogs) ──> core (process runner)
               └──> Dear ImGui, GLFW
   (* macOS only, ** Linux only; the ffmpeg / ffprobe executables are run as child processes, not linked)
```

Arrows point from user to used; nothing points the other way. `core` never includes ImGui, GLFW or GL, so
it builds and runs headless (that is what the tests, `cc_bench`, `--check-config` and `--system-info` rely
on). The feature macros `CC_HAVE_CURL` and `CC_HAVE_WINHTTP` are always defined as 0 or 1; the WinHTTP path
and the other `#ifdef _WIN32` branches in the source are not part of this port's builds.

## The core library, file by file

| File | Responsibility | Notable design points |
|---|---|---|
| `core/config.h/.cpp` | typed `Config` struct mirroring `config.yaml`; `load_config` (built-in + override, deep merge, sites by name), `parse_config`, `find_config_override`, `default_config` | every key validated with a named bound, unknown keys rejected, cross-field rules; iterative merge and walk (no recursion); yaml-cpp exceptions caught at the two public entry points; `user_config_path()` gives the per-user override (`~/Library/Application Support/CompressCompare/config.yaml` on macOS, `$XDG_CONFIG_HOME/compresscompare/config.yaml` or `~/.config/compresscompare/config.yaml` on Linux), searched after the executable's folder and before the working directory |
| `core/accel.h/.cpp` | `init_acceleration()`: OpenCV thread count, OpenCL device selection (`OPENCV_OPENCL_DEVICE`), kernel build and, in `auto` mode, the GPU-against-CPU self-test; `AccelStatus` (shown by `--system-info` and in Settings); `set_opencl_enabled()` for the Settings checkbox; `use_gpu_for(pixels)` | the single place that decides whether OpenCL is used; a CPU-only device is refused in `auto` mode; `use_gpu_for()` applies `acceleration.min_gpu_pixels` and sets OpenCV's per-thread OpenCL switch |
| `core/cl_kernels.h` | OpenCL C 1.2 source of the kernels OpenCV has no built-in for: the per-pixel metrics, the three maps the statistics reduce, Rec.601 luma, the SSIM combination, sRGB ↔ linear light with premultiplied alpha | no double precision, no images, no extensions (what macOS 12 offers on Intel HD graphics); the colour constants are the same standards constants as in `metrics.cpp` |
| `core/cv_ops.h/.cpp` | `cc::cvops`: launches those kernels on `cv::UMat` through OpenCV's Transparent API, each with an identical CPU twin; `build_kernels()`, `self_test()` | when a kernel cannot run the CPU twin is used, so callers never handle an OpenCL failure; CPU rows are split over OpenCV's thread pool (`cv::parallel_for_`) |
| `core/metric.h/.cpp`, `core/view_mode.h/.cpp`, `core/colormap.h/.cpp` | the enums `Metric`, `ViewMode`, `ColorMap` with their display names, config keys and help texts; colour-map evaluation and 256-entry tables | the config file and the UI share one key spelling per enum |
| `core/image.h/.cpp` | `Image` (8-bit RGBA), file reading, byte sniffing (JPEG, PNG, GIF, BMP, TIFF, WebP, AVIF/HEIF, ISO-BMFF video, Matroska, FLV, MPEG-PS, Ogg, ASF, HTML), decoding with `cv::imdecode` (then ImageIO on macOS), `resample`, crop, cover-fit, PNG writing with `cv::imencode` | type is detected from bytes, never from the name; header sizes of JPEG, PNG, GIF, BMP and WebP are checked against the edge limit before decoding; JPEGs are decoded with their EXIF orientation applied; `resample` works in linear light with premultiplied alpha (`INTER_AREA` when shrinking in both directions, `INTER_CUBIC` otherwise); `cv::Exception` is caught around `cv::imdecode` and `cv::imencode` |
| `core/imageio_apple.h/.cpp` | macOS only: HEIC/HEIF (and AVIF on macOS 13+) through ImageIO, with the orientation applied and conversion to sRGB | C APIs of CoreFoundation / ImageIO / CoreGraphics, no Objective-C |
| `core/jpeg_info.h/.cpp` | marker walker: DQT, SOF, APP0/1/2/14; IJG quality inversion; subsampling; summary line | segment loop bounded by `kMaxSegments`; pure functions on a byte range |
| `core/metrics.h/.cpp` | sRGB→Lab, ΔE76/ΔE2000 (used by the CPU twins and the hover read-out), `compute_heatmap`, `HeatMap` with percentiles and histogram, `compute_stats` → `PairStats`, SSIM map, block averaging | the pipeline runs on `cv::UMat`: kernels from `cv_ops`, `cv::GaussianBlur` (`BORDER_REPLICATE`) for the SSIM moments, `cv::mean`, `cv::minMaxLoc`, `cv::compare` and `cv::countNonZero` for the statistics; the map is copied back once for percentiles, histogram and block view; physical constants are named `constexpr` values, not config |
| `core/fuzzy.h/.cpp` | Sublime-style subsequence scorer with alias support | iterative dynamic programme with explicit back pointers; inputs truncated to `kFuzzyMaxPatternChars` / `kFuzzyMaxHaystackChars` |
| `core/sites.h/.cpp` | host-suffix detection and name/alias lookup over `Config::sites` | the database itself lives in `config.yaml` |
| `core/net.h/.cpp` | `fetch_url` with libcurl (the macOS SDK's on macOS), or a stub when the build has no libcurl | size cap enforced while reading; time-outs, redirect limit and headers from `network.*` |
| `core/process.h/.cpp` | `run_process` (argv, time-out, output cap) on POSIX; `executable_dir`; `find_program` | no shell involved; child killed on time-out; reads bounded by `process.max_read_iterations` |
| `core/video_cv.h/.cpp` | video through `cv::VideoCapture`: `probe_video_opencv`, `extract_frame_opencv`, and `isobmff_video_track` / `isobmff_file_video_track` (`IsoTrackInfo`: the first video track's display rotation from its `tkhd` matrix and its codec from the `stsd` sample-entry FOURCC) | AVFoundation on macOS (hardware H.264/HEVC decoding, no external program), FFmpeg libraries on Linux. The FFmpeg back-end reports the codec (`CAP_PROP_FOURCC`) and rotates frames itself. AVFoundation does neither – its `CAP_PROP_FOURCC` is the output pixel format – so for it the codec (`avc1` shown as `h264`, `hvc1` as `hevc`) and the rotation come from the MP4/MOV headers (`CAP_PROP_ORIENTATION_META` when the `tkhd` rotation is 0), and the rotation is applied to every frame; open captures are cached per thread so scrubbing does not reopen the file |
| `core/ffmpeg.h/.cpp` | `VideoInfo` (with `backend`: `OpenCV AVFOUNDATION`, `OpenCV FFMPEG` or `ffmpeg`, and `frame_rotation`), `FfmpegTools`, `locate_ffmpeg`; `probe_video` / `extract_frame` dispatch to OpenCV first and to the `ffprobe` / `ffmpeg` executables as fallback (`acceleration.video_backend`); still decoding via ffmpeg | videos are never fully decoded in memory; caps from `limits.video.*` checked before and after probing; `VideoInfo::rotation` uses ffprobe's convention whichever back-end probed |
| `core/threading.h/.cpp` | `worker_thread_count`, `parallel_for`, `Progress`, `BackgroundWorker` (one job thread, completions delivered on the main thread by `poll()`) | the pixel loops run on OpenCV's pool; `parallel_for` (and `threading.min_rows_per_worker`) is kept for compatibility |
| `util/strings.h` | trim, lower-case, `ends_with`, URL host / extension, byte formatting | header-only, `[[nodiscard]]` throughout |
| `util/contract.h/.cpp` | `CC_REQUIRE(cond, recovery)` and `CC_ENSURE(cond)`: print file and line, count, then recover | assertions that stay on in release builds without aborting |

| `app/ui_slots.cpp` | left panel: slot cards, drop zones, URL line, site combo, *Visualize compression* |
| `app/ui_compare.cpp` | the canvas: keyboard shortcuts, toolbar, the six layouts, split divider, mouse zoom/pan, hover read-out, corner loupe (`ViewerFrame` holds one frame's geometry) |
| `app/ui_panels.cpp` | menus, status bar, right panel (heat map controls and legend, statistics and histogram, alignment nudge, video timeline and sampling), the Settings window (acceleration, video limits and ffmpeg, downloads, display, the settings-file path and *edit config.yaml...*) and the about window with the credits |
| `app/fuzzy_combo.h/.cpp` | the *Specify site* text box with its ranked dropdown, plus `InputTextStd` and `HelpTooltip` |
| `app/ui_style.h` | cosmetic constants (paddings, colours, buffer sizes) that are not user settings |
| `gpu/gl.h/.cpp` | 47 explicitly declared OpenGL 3.3 entry points resolved through `glfwGetProcAddress`; no GLEW/glad |
| `gpu/shaders.h`, `gpu/renderer.h/.cpp` | one vertex + one fragment shader that draw a textured quad with the heat-map colour ramp, overlay blending, threshold, gamma and split masks; `GpuTexture` upload; issued from an ImGui draw callback |
| `platform/dialogs.h/.cpp` | open/save dialogs: `/usr/bin/osascript` on macOS, `zenity` / `kdialog` subprocesses on Linux; `open_user_config` for the Settings button *edit config.yaml...*: creates the per-user file from the built-in defaults (with a two-line header comment) if missing and opens it with `/usr/bin/open -t` (TextEdit) on macOS or `xdg-open` on Linux |
| `main.cpp` | `parse_command_line` (including `--system-info`; Finder's `-psn_…` argument is ignored), configuration loading, `init_acceleration`, GLFW window + OpenGL 3.3 core forward-compatible context, ImGui set-up (DPI scale, tooltip delays, `ui.ini` location), the power-saving main loop (`glfwWaitEventsTimeout` with `app.frame_timing`), exit-time contract report |

On macOS, window sizes and ImGui coordinates are in points: the monitor scale is taken as 1 and GLFW's
framebuffer scale supplies the Retina pixels.

### Threads

- The **main thread** runs GLFW, ImGui and all OpenGL calls. It never blocks on I/O. It calls
  `init_acceleration()` once before the window opens, so the OpenCL device is chosen and the kernels are
  built and tested before any image work starts.
- The **background worker** (`BackgroundWorker`, one thread) runs one job at a time: loading and decoding a
  file, downloading, probing or seeking a video, computing statistics or a heat map, sampling a video. A
  job returns a completion closure that the main thread executes in `poll()`, so results (images, textures)
  are handed over without locks in app code. Jobs report through `Progress` (fraction, label, cancel
  flag).
- **OpenCV's thread pool** (`threading.max_workers`, capped by the core count, set once in
  `init_acceleration()`) runs OpenCV's own functions and the CPU twins' row loops for the background job.
- **OpenCL is switched per thread.** OpenCV's `cv::ocl::setUseOpenCL()` flag belongs to the calling thread;
  every operation calls `use_gpu_for(pixels)` on the thread that runs it, which combines the global switch
  (start-up result and Settings checkbox) with `acceleration.min_gpu_pixels`.
- **External programs** (`ffmpeg`, `ffprobe`, dialog helpers) get a short-lived helper thread that drains
  their stderr; it is joined before `run_process` returns.

### Data flow of one comparison

1. A `Slot` receives a path or URL → job: read/download bytes, sniff, decode (OpenCV imgcodecs, then ImageIO
   on macOS, then the ffmpeg executable as the last fallback; for a video: probe + extract a frame through
   OpenCV or ffmpeg) → `MediaSource` with the native image, `JpegInfo`, `VideoInfo`, the decoder's name and a
   thumbnail texture.
2. *Visualize* → job: pick the comparison size (site size, or original size when *compare at site
   resolution* is off, capped by the GPU texture size), cover-fit and resample both images (sRGB-aware, in
   linear light, through OpenCL when enabled), compute `PairStats` → `Comparison` with before/after images
   and textures.
3. The heat map for the selected metric is a second job (`compute_heatmap`: upload to `cv::UMat`, the
   metric kernel or the SSIM chain, one download, then percentiles and histogram on the CPU; optionally
   `block_average`), cached per metric in the `Comparison`; changing the metric or block view starts a new
   one.
4. Every frame, the renderer draws the before/after/heat textures through the compare shader with the
   current `DrawParams` (zoom, split, overlay mode, intensity, threshold, gamma, colour-map table).

## Build system

`CMakeLists.txt` keeps the two targets, the tests, `cc_bench` and the analysis targets. On macOS it sets the
deployment target to 12.0 and the architecture to x86_64 before `project()`, builds `compresscompare` as the
`CompressCompare.app` bundle (Info.plist from `packaging/macos/Info.plist.in`, the icon in
`Contents/Resources`; no `config.yaml` is copied into the bundle), links the Cocoa, IOKit, CoreVideo, ImageIO, CoreGraphics and
CoreFoundation frameworks and defines `GL_SILENCE_DEPRECATION`.

`cmake/Dependencies.cmake` takes OpenCV 4.6 or newer from `deps/opencv` (built by `scripts/build-deps.sh`:
OpenCV 4.12.0, static, OpenCL on, IPP on by default, AVFoundation on macOS, FFmpeg on Linux) or from
`OpenCV_DIR` / an installed copy. Every other dependency is looked up with `find_package`, then a pkg-config
module, and finally fetched with `FetchContent` from GitHub (Dear ImGui v1.92.9b always; GLFW 3.4 and
yaml-cpp 0.8.0 when missing). libcurl is optional and comes from the macOS SDK on a Mac.
`cmake/EmbedFile.cmake` regenerates `build/<preset>/generated/cc_builtin_config.h` whenever
`config/config.yaml` changes, so a configuration edit is a rebuild, not a reconfigure.

`scripts/build-macos.sh` wraps all of it for macOS ([Build on macOS](../how-to/build-macos.md)); Linux
uses the `linux-system` preset ([Build on Linux](../how-to/build-linux.md)).
